# Phases 3 and 4 — delivery notes

Build 0.4.0, 15 November 2026. The native Rust engine/studio now implements a bounded entity, sensor and experiment workflow. Phase 5 remains the complete v1 qualification and release milestone. This report records actual behaviour and remaining limits rather than treating phase labels as proof of scientific or visual acceptance.

## Phase 3 implementation

The shared engine has configurable submerged and surface bodies, diagonal translational added mass, quadratic relative-water drag, sampled partial immersion, depth-dependent density, an offset centre of buoyancy, actuator lag/saturation and depth/heading PD controllers. The reference ROV uses a six-thruster geometry and a bounded iterative wrench allocator. Surface vessels and passive floats have separate geometry/displacement defaults. Contact-enabled bodies substep at up to 120 Hz; legacy bodies preserve their original fixed-step path.

Terrain contacts sample the body support footprint. Structures use expanded box proxies. Vehicle pairs use X-axis sweep-and-prune plus conservative world-space box overlap, low-restitution impulses and positional correction. These are deliberately bounded proxy models, not convex-mesh contact, continuous collision detection or a full calibrated six-DOF hydrodynamic model. Contact does not resolve angular impulses at a geometric contact manifold. Added-mass/restoring terms are approximations; full off-diagonal Fossen coupling is not claimed.

The reference fish model has a shaped body, fins, eyes and animated tail, with bounded swimming acceleration, local separation/alignment/cohesion, depth/region preferences, current response and avoidance steering. A spatial hash bounds neighbour searches. It is a generic schooling model, not a validated species or ecological forecast. Fish are steerable agents rather than rigid contact bodies. Distant fish are culled in rendering; behaviour remains independent of the camera. Passive tracers use midpoint current advection. The authored seagrass patch and tail motion are cosmetic.

Authoring supports entity selection, placement by XYZ/heading fields, mass/displacement and actuator controls, controller enable/disable, contacts, duplication/deletion and undo/recovery. Selected bodies have visible axis markers; direct drag gizmos and a thumbnail asset catalogue remain polish work. The native file browser imports geometry-only OBJ with bounded vertices/faces and embeds it in the scene. Imported geometry uses an explicit box contact proxy. Materials/textures from arbitrary OBJ/MTL packages are not loaded.

## Phase 4 implementation

The sensor suite supports an attached camera, a geometric multibeam fan, depth/position/velocity observations, angular rate and sampled specific force. Rate, mount, field of view, range, fan, noise and delivery latency are configurable. Truth and delivered measurements remain separate. Scheduling uses integer simulation ticks; the effective rate is the nearest fixed-tick divisor. For example, 10 Hz is exact at 60 Hz; arbitrary requested rates may be quantised.

Sonar intersects the same terrain/structure/body proxies used by the world. Travel time integrates the approximate water sound-speed profile along eight straight-ray segments. Intensity uses simple spreading, absorption, incidence and target-class reflectivity. Range/navigation/IMU noise is seeded. There is no ray bending, coherent speckle, multipath, calibrated beam pattern or validated acoustic backscatter model. The attitude quaternion is truth orientation; the angular-rate and specific-force outputs have explicit noise. Specific force uses differences between sampled truth velocities and includes gravity in the sensor/body frame.

Live runs record truth samples, delivered observations, a full initial dynamic checkpoint, fixed dt, seed, scene/assets/data, model settings, engine version/build fingerprint and timed force/torque changes. A recording can begin mid-session. Playback presents stored truth without advancing the live world. Re-simulation restores the checkpoint, applies the control timeline and compares truth at every saved sample. Divergence is reported explicitly. Cross-platform/compiler identity is not promised; observations are preserved for playback, while the current verifier checks physical truth rather than claiming a field-data match.

The experiment workspace provides recording, open/save, scrub-by-sample, previous/next, depth/speed traces, cancellable headless batches, verification and exports. Completed live and background runs receive unique recovery copies under `%LOCALAPPDATA%\Pelagic\Runs`. Physical scene edits archive an active recording before rebuilding the preview. Closing waits for pending run backups; background tasks must finish or be cancelled before closing. A failed backup leaves the in-memory recording available for export.

Dataset bundles include the scene, full JSON recording, manifest and CSV tables for truth, sonar, navigation/IMU, fish and commands. Camera datasets add up to 120 recorded-truth images with timestamps, pose, intrinsics and source stride. Images are 320×200 RGB PPM; individual mounted-camera export also provides PNG plus calibration JSON. The camera is a pinhole renderer with illustrative underwater optics, not a calibrated camera/rolling-shutter model. Incomplete camera exports retain an explicit marker.

The public Rust scene model is shared by desktop and headless execution. A versioned C ABI/DLL has an independently loaded host example. A loopback-only MAVLink 1 adapter accepts MANUAL_CONTROL and publishes LOCAL_POSITION_NED plus heartbeat, with explicit FLU/NED conversion and a one-second command watchdog. A separate-process UDP smoke test exercises it. This is a tested protocol subset, not a claim that ROS 2, QGroundControl or a particular physical robot was installed and qualified here. See SDK.md.

## Regional data and portability

The app includes a NOAA ETOPO1-derived 2° global overview and a 1-arc-minute Goa offshore subset. The regional subset is resampled to an isotropic local metre grid with its geographic origin retained. It is a resampled composite elevation product; the metadata does not label it as a direct local survey. Waves, currents, fish and other synthetic content are identified separately from that terrain.

Supported inputs are rectangular SI elevation CSV/TXT, ESRI ASCII grids, bounded ERDDAP-style latitude/longitude/altitude CSV and complete regular XYZ/time current CSV. Missing data, duplicate current samples, irregular axes and invalid numeric shapes are rejected rather than silently filled. Units follow the stated input contract; the loaders do not infer or convert an unknown coordinate system. Local geographic import is non-polar and bounded to one degree per axis; it is not a global projection library. The overview is coarse coverage, not global high-resolution scene streaming. Arbitrary regions need a supported user-supplied dataset; generating a synthetic region does not invent measured seafloor data.

Schema v4 embeds grids, imported meshes, flow fields, entities, sensor setup and provenance. Versions 1–3 migrate; unknown future versions are rejected. Projects have a 16 MB portability budget, and imports have bounded source/sample counts. Runs use schema v1 with a 64 MB file limit and 1,200 samples. Batch duration/rate combinations exceeding that capacity are rejected up front. Meshes, fields and records retain stated SI/Z-up conventions; assets do not depend on their original external paths.

## Verification and remaining acceptance

Automated tests cover analytic motion/dispersion, settling, added mass/actuator limits, allocator residuals, depth/heading convergence, contact separation and pair momentum, deterministic schooling, sensor geometry/timing/noise, real-data coordinates, parser rejection, dataset self-containment, checkpoint/control-timeline reproduction, persistence/history/recovery and UI control/label bounds. The actual DLL host and UDP adapter are exercised separately. Generated app previews cover life, entities, sonar, results, atlas and both themes; no user-desktop inspection is needed.

The bounded workflow is ready for product review. Remaining Phase 5 work includes substantial graphics/asset polish, accessibility/UI Automation, direct manipulation and richer browsing, sustained full-app/hardware profiling, larger-data streaming, installer/update/signing decisions, independent numerical/field comparisons and long-run/extreme-state qualification. The current implementation does not establish full roadmap gate sign-off or operational accuracy. See ROADMAP.md for the full v1 contract.

Model references: [Fossen’s marine craft equations](https://www.fossen.biz/html/marineCraftModel.html) describe the richer coupled model against which this approximation should be compared; [Reynolds’ steering work](https://www.red3d.com/cwr/steer/gdc99/) supplies the behavioural basis. These references explain the models; they are not validation results for Pelagic.
